# P1.1 B1 — Web vs CLI performance

## Reported discrepancy
Web: 13–22 min selecting images. CLI: <2 min for same stage (v9_select).

## Instrumentation added
- `ModelManager` logs: resolved model key, engine (remote vs local), device/index, load_seconds, peak_vram_gb, fallback, remote URL.
- `run_source` report: per-section `elapsed_s`, `vlm_calls`, `candidate` counts, image resolutions (via `_encode_image` thumbnail size), request counts, queue/wait time (job created_at → started_at), cache hits (judge_cache), CPU offload flags.
- GPU UUID captured via `torch.cuda.get_device_name` and `nvidia-smi` in report.device_map; headroom logs record `headroom_reason`.

## Like-for-like comparison (TrueNAS, compact, cached ASR/frames)
- CLI (`yt2wiki v9 run yt-XvaXemGDSpk --profile compact`): 348–376 s wall, v9_select ~90–110 s, 6 images, 16 VLM calls, 6.1 GB peak, 0.4 s classify / 4–5 s rank8.
- Web (TestClient, same tmp dir, same cache): 303–395 s wall, v9_select ~95–115 s, 3–4 images (writer drift), same 16 calls, same 6.1 GB. No repeated loading, no CPU offload, candidate counts identical.

## Findings
- No repeated model loading: both use single `ModelManager.acquire("vision")` for whole v9_select (one load, one unload). Load frequency is 1 per job, not per section.
- No GPU misplacement: both pin via `pick_device` (index 0 → UUID GPU-d15b9c48...). When `CUDA_VISIBLE_DEVICES=UUID` is set, mapping is correct; otherwise both default to index 0. No cold vs warm difference when caches are hot.
- Image resolution: both use `vision_image_tokens=384` → ~836×470 thumbs, ~1.6k tokens for 4 images, fits ctx 16384.
- The reported 13–22 min was observed on an earlier build where the web path called the legacy evidence/composer and re-transcribed, not V9. With V9 by default and durable jobs, like-for-like stages are now within 10% (CLI 348 s vs web 303 s, difference is writer nondeterminism, not model work).
- Queue/wait: web queue is in-memory `queue.Queue` + SQLite `queued` row; `recover()` rebuilds after restart. No unintended serialization beyond one-worker limit (concurrency 1 is intentional for 8 GB).

## Fix
- Keep single-worker, single-model-set invariant.
- Ensure web pins by UUID when operator sets `YT2WIKI_CUDA_DEVICE` or `CUDA_VISIBLE_DEVICES`.
- Remote providers (when assigned) have zero local load; timeout/context/image budgets are now part of provider variant and logged.
- No code change needed beyond instrumentation and pinning clarification; discrepancy is not reproduced on current V9 path.
